# Garbage Collection

Source: [ticket 11](../../.scratch/spec/issues/11-gc-design.md).

Policy: **storage quota + LRU, root-first and closure-safe**.

## Eviction

An object is evictable only when **no surviving referrer** exists in the
cache (`NOT EXISTS` against `object_refs.reference`; ref rows
cascade-delete with their referrer). Candidates are evicted in
last-accessed order. Old roots (stale system generations) go first;
deleting them frees their dependencies for the same pass's next
iteration. The pass loops until usage reaches the low watermark or no
candidates remain — every surviving root's closure stays complete.

**Pins** (ticket 22) are GC-exempt roots: `garret-admin pin <name>
<hash> [--expires <duration>]` records the root in the `pins` table
(pinning a hash not in the cache is a hard error), and the candidate
query excludes every live pin — one whose `expires_at` is null or in the
future. Only the root needs excluding: eviction is root-first, so the
surviving pinned row keeps its whole closure referenced and therefore
protected, with no closure walk. An expired pin simply stops matching the
query — no sweep. Pinned bytes still count toward quota: a quota made
entirely of live pins surfaces as the candidates-exhausted alarm below,
not silent thrashing. `garret-admin unpin <name>` removes a pin; the pin
listing is the browse API's `GET /api/v1/pins` (spec 07).

If candidates are exhausted while still above the low watermark
(everything referenced), GC stops and raises an alarm metric rather than
breaking closures.

## Prune by push age

`garret-admin prune --before <YYYY-MM-DD | age> [--apply]` deletes every
closure last pushed before the cutoff, regardless of quota. It keeps
every object pushed at or after the cutoff, every live pin, and each
one's whole reference closure, then deletes everything else
(mark-and-sweep). The mark is one recursive CTE, a plain read. Store paths
form a DAG (self-edges aside), so the deleted set is exactly what
repeated root-first deletion of old objects would reach, and every
deleted object is older than the cutoff by construction. Rows go first,
blobs second, as in eviction. Without `--apply` it only lists what it
would delete.

Age is `objects.pushed_at` (spec 02), not `created_at`: CI re-pushing an
unchanged closure uploads nothing, but its Negotiation marks every path
it names as pushed now. Without that, a system closure unchanged for
months would look old while still in daily use.

The same mark closes the Negotiation race. A client told a path is
present relies on it until its uploads finish; the path's `pushed_at`
is at most `PUSHED_AT_DEBOUNCE` (1 h) behind that Negotiation, and the
cutoff must be at least 24 h in the past, so a prune that runs mid-push
keeps the closure. Prune holds the Pusher's writer connection from mark
to last delete, so Negotiation and uploads pause while it runs; the
deletes commit in batches of 500, referrers before their references, so
the Puller's writes interleave and the cache is closed after every
commit. A dry run takes no SQLite write lock at all.

## Trigger and accounting

High/low watermarks, defaults **95% / 85%** of quota, all configurable.
Usage is the maintained `stats.total_bytes` counter (updated in the same
transaction as inserts/deletes), reconciled against `SUM(file_size)` each
pass.

## Placement and mechanics

- GC runs as a background task **inside the Pusher** (single-writer
  discipline holds; the orphan sweep can consult in-memory in-flight
  upload state). Each timer tick is a cheap counter check; eviction work
  only happens past the high watermark. `garret-admin gc run` triggers a
  pass on demand.
- Delete order: **DB row first, blob second** (preserves row ⇒ blob; a
  failed blob delete leaves an orphan for the sweep). A key that a `200`
  `DeleteObjects` response lists under `Errors` is a failed delete too:
  it is logged, counted in `garret_s3_delete_failures_total`, and fails
  the GC pass, sweep, or admin command once every batch has been tried.
  `NoSuchKey` is the exception — the blob is already absent (a dangling
  row, say), which is the goal; Garage reports it there where S3 reports
  the key as deleted.
- S3 deletes use `DeleteObjects` batches of 1,000 with bounded,
  configurable concurrency.

## Orphan sweep

At startup and weekly: list the bucket against the DB; delete blobs with
no row older than 24 h; abort multipart uploads not in the in-flight set
past the same threshold.

## `garret-admin fsck`

The orphan sweep cleans up after normal operation; `fsck` audits for
drift a sweep never sees — a manually deleted S3 object, an interrupted
restore, bucket corruption. It runs on the admin socket (so repair goes
through the Pusher's single writer connection) and is **online by
default**, using the same two guards as the orphan sweep: an in-flight
upload is never mistaken for a defect, and neither is anything younger
than `orphan_grace_secs`.

- Lists S3 keys **before** DB rows — the same order the in-flight/age
  guards protect against, so a push landing in the gap between the two
  listings looks exactly like the race those guards already close.
- Reports **dangling rows** (row, no blob, past both guards) and
  **orphan blobs** (blob, no row, past both guards — informational only;
  the orphan sweep still owns deleting these on its own schedule).
  `--verify-sizes` adds a third category, **size mismatches**: a row and
  blob both exist but `file_size` disagrees with the S3 object's size.
- `--repair` deletes dangling and size-mismatched rows via the same
  `db::delete_object` GC uses — never the S3 object; a size-mismatched
  row's now-orphaned blob is left for the orphan sweep. Dry-run (report
  only) is the default.
- `--repair --quiesce` is the offline fallback for when the live
  in-flight signal alone isn't trusted enough to delete rows on: it sets
  a reject-new-pushes flag, waits (bounded, default 300 s) for in-flight
  uploads to drain, and only then repairs. A timed-out drain reports
  `quiesce_drained: false` and repairs nothing; the flag is always
  cleared before the command returns.
