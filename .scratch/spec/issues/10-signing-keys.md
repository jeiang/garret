# Narinfo signing and key management

Type: grilling
Status: resolved

## Question

Design the ed25519 cache-signing story: key generation and storage (file on
host? admin CLI command?), rotation (nix supports multiple
trusted-public-keys — is rotation a supported flow?), whether narinfos are
signed at write time (stored) or at serve time (computed, cacheable — see
`OPTIMIZATIONS.md` item 8), and which admin CLI operations key management
needs.

## Answer

**Sign on write.** The Pusher signs the narinfo fingerprint when the
object row is inserted; signatures are stored in a `sigs` column (ticket
07's conditional column is now confirmed). The public Puller's narinfo
path does zero crypto — it serves stored rows. This supersedes
`OPTIMIZATIONS.md` item 8's serve-time signature caching: nothing to
cache.

**Multi-key overlap rotation.** Config holds an ordered list of signing
keys — one active, optionally one retiring. New uploads are signed by all
listed keys (narinfos carry multiple sigs; nix accepts any trusted key).
`garret-admin resign` backfills existing rows with a newly added key.
Rotation flow: add new key → resign → migrate clients'
trusted-public-keys at leisure → remove old key from config. No flag day.

**Key format and storage** — standard nix key format
(`<name>:<base64-ed25519>`), key name configurable (e.g.
`cache.example-1`, incrementing suffix per rotation). Secret key is a
file on disk referenced by config path — generated by `garret-admin key
generate`, deployable via the NixOS module's secrets-path option
(agenix/sops-friendly; the module never puts key material in the nix
store).

**Admin CLI surface fed to spec assembly** — `key generate`, `key show`
(public key for nix.conf), `resign`.
